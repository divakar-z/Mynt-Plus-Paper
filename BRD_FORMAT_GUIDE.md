# BRD Authoring & Format Guide — Mynt Plus

A reference for producing **Business Requirements Documents (BRDs)** for Mynt Plus
features in the house format used by `WEB_PLACE_ORDER_INTRADAY_BRD.docx` and
`INSTAOPTIONS_ANALYTICS_BRD.docx`. Follow this and every BRD comes out consistent,
tester-ready, and correctly styled.

> **What a BRD in this house style is:** a lean, tester-facing document that a QA
> engineer (internal or third-party vendor) can execute top to bottom without
> knowing the code. It is organised as a series of **cases**, each a small table
> of *Description → Test Steps → Expected Result → Code Reference*. It is **not** a
> requirements matrix — see §8 for what to leave out.

---

## 1. The deliverable at a glance

- **Final format:** a Microsoft Word **`.docx`** in the house style (navy table
  headers, zebra rows, bold labels, monospace code refs, a Table of Contents).
- **Authored in:** Markdown, converted with **Pandoc** using an existing house BRD
  as the style template, then a short **post-processor** applies the table look.
- **Naming:** `<AREA>_<FEATURE>_BRD.docx` (e.g. `WEB_PLACE_ORDER_INTRADAY_BRD.docx`,
  `INSTAOPTIONS_ANALYTICS_BRD.docx`).

The house table look (navy header + zebra + bold labels) is **direct cell
formatting**, not a Word table style — which is why the post-processor in §9 is
required. Pandoc alone produces plain, borderless tables that read as loose text.

---

## 2. Document structure (in order)

| Order | Element | Heading level | Notes |
|---|---|---|---|
| 1 | Title | `#` H1 | `<Feature> — Business Requirements Document` |
| 2 | Table of Contents | (auto) | Generated by Pandoc `--toc`; sits above the title |
| 3 | Document Control | `##` H2 | 8-field table (§4) |
| 4 | Scope | `##` H2 | Prose, 2–3 paragraphs (§5) |
| 5 | `SECTION N — NAME` | `#` H1 | One per major grouping (§6), with a tester note |
| 6 | `N.x Subsection` | `##` H2 | Groups cases within a section |
| 7 | `<ID> — <title>` | `####` H4 | One per **case**, followed by the case table (§7) |

**Organise by the tester's natural run order** — segment by segment (Equity / F&O /
MCX) or screen by screen — so one section can be executed top to bottom. End with a
**"COMMON BEHAVIOURS"** section for anything that applies across the whole feature.

A copy-paste skeleton is in [§11](#11-copy-paste-skeleton).

---

## 3. Heading levels — fixed mapping

Do not deviate; the styling depends on it.

- `#` (H1) → the document title **and** each `SECTION N — NAME`.
- `##` (H2) → `Document Control`, `Scope`, and each numbered subsection `N.x …`.
- `####` (H4) → each case heading `<ID> — <title>` (renders as the blue case title).
- Never use H3; never use H5+.

---

## 4. Document Control table

Always exactly these eight rows, `Field | Detail`:

| Field | Detail (guidance) |
|---|---|
| Document Title | `<Feature> — Business Requirements Document` |
| Product | `Mynt Plus — Web Trading Platform` |
| Module | The feature/module and the order type or sub-area |
| Platform | `Web` (or `Mobile`, etc.) |
| Owner | `Zebu Trade` |
| Last updated | ISO date `YYYY-MM-DD` |
| Status | `Issued for Review` → `Approved` → … |
| Classification | `Internal Use Only` (or `Confidential` for external hand-off) |

Keep it to these eight. Do **not** add a revision-history table or an approvals grid
unless explicitly asked — the house format is lean.

---

## 5. Scope section

Two or three short paragraphs, in this shape:

1. **What is covered** — one sentence naming the feature and the surfaces it spans
   (the screens / segments / order types), plus any one-line context a tester needs.
2. **Coverage** — a sentence listing the kinds of things covered: default states,
   every field/control, all the scenarios, the validations, the common behaviours.
3. **Organisation & boundaries** — "organised <segment/screen> by <…> so a tester can
   run one top to bottom", then what is **out of scope** (and where it lives, if it
   has its own doc), and any environmental caveat (e.g. market-hours-only "Live"
   cases; read-only module places no orders).

Keep it factual and short. Do **not** narrate prior versions or migration history.

---

## 6. Sections & the tester note

- Title a section `# SECTION N — NAME` (all caps name).
- Immediately below, add a **`Note for the tester:`** paragraph whenever there is a
  cross-cutting fact the tester should hold in mind for every case in the section
  (e.g. "every case applies to both NSE and BSE; the only differences are …", or
  "the socket overlay runs only on these screens").
- Group cases under `## N.1 <topic>`, `## N.2 <topic>` subsections.

---

## 7. The case — the core unit

### 7.1 ID scheme

- A short **prefix** identifies the feature: `PO` = Place Order, `IO` = InstaOptions.
  Pick a 2–3 letter prefix per BRD and keep it consistent.
- Zero-padded numbers, **left with gaps between groups** so cases can be inserted
  later without renumbering — e.g. `IO-001…005` (global), `IO-010…015` (screen 1),
  `IO-020…028` (screen 2). Common-behaviour cases often start at `-100`.
- IDs are unique and never reused.

### 7.2 Case heading

`#### <ID> — <concise behaviour> (<qualifier>)`

Examples: `#### IO-033 — Ladder: mirrored OI bars, null legs, spot line, no Greeks`,
`#### PO-041 — Place an Intraday Buy Market order (Equity — NSE/BSE)`.

### 7.3 The case table — four content rows

Under a `Field | Detail` header, always these four rows in this order:

| Row | What goes in it |
|---|---|
| **Description** | Prose (2–5 sentences): what the feature/control does, plus the context or business rule a tester needs. State defaults and any mode interactions. |
| **Test Steps** | A **numbered** list of concrete, real-world actions — what to click, type, and observe. One action per step. Name exact controls/labels ("click the **B** button", "select the Intraday tab"). |
| **Expected Result** | A **bulleted** list, each bullet tied to a step: `Step N: <verifiable outcome>`. Quote UI/validation messages **verbatim** in quotes. Append `Live — requires an open market.` (or similar) when the case needs a specific environment. |
| **Code Reference** | Comma-separated `file.dart:line` anchors to the implementing code (rendered monospace). Keep to real paths/lines; a bare filename is fine when a line range is not meaningful. |

Because the cells contain lists, author these as **Pandoc grid tables**, not pipe
tables (pipe tables cannot hold lists). See §9.1.

---

## 8. Writing style — do & don't

**Do**
- Write for a tester with no code knowledge: concrete, physical actions and
  observations ("Hover over a scrip and click the **B** button").
- Quote every UI label, button, and validation message **verbatim**.
- One action per Test Step; one verifiable outcome per Expected bullet.
- For mirror cases, reference the primary instead of repeating ("The mirror of
  PO-039 — Sell side; all input validations behave identically").
- Mark environment-dependent cases (`Live — requires an open market.`).
- Use em dashes for asides. Keep Rupee `₹` and `%`; prefer words over exotic symbols
  inside table cells (keeps the grid-table source clean).

**Don't** (this is the "remove the noise" rule)
- No Requirements Traceability Matrix, no separate Business/Functional/Non-Functional
  requirement sections, no priority-tag scaffolding — unless explicitly requested.
- No revision-history padding, no "known non-defects" appendix, no references to
  prior or legacy versions (only state a real out-of-scope boundary).
- No embedded credentials or live URLs — provide those to the vendor separately.

## 9. Visual / formatting spec (the house look)

Applied by the pipeline in §10; these are the exact values.

| Element | Spec |
|---|---|
| Table header row | Fill `#1F3A93` (navy), text **bold white** (`#FFFFFF`); repeats on page breaks |
| Body rows | **Zebra**: fill `#F7F8FC` on alternating rows (2nd, 4th, …), others no fill |
| First column (labels) | **Bold** |
| Code Reference values | Monospace (Consolas), slightly smaller |
| Cell borders | **None** (the fills carry the structure) |
| Case title | Heading 4 (blue bold italic in the house template) |
| TOC | Present, depth 2 (sections + subsections) |
| Fonts, margins, heading styles | Inherited from the reference `.docx` template |
| Case-table columns | 2 columns; label ≈ 20 %, detail ≈ 80 % (readable). The reference uses 50/50 — either is acceptable |

### 9.1 Grid-table authoring rule

Each case table is a **2-column Pandoc grid table**. Label column ~22 chars wide,
detail column ~92 chars. Lists inside a cell use normal Markdown markers
(`1.` for Test Steps, `-` for Expected). Wrap long lines to the column width;
continuation lines indent under the list marker. Generate these programmatically
(a tiny helper avoids hand-aligning `+`/`|`) — see §11.

## 10. Production pipeline

Prerequisites (macOS): `brew install pandoc` and, for faithful preview,
`brew install --cask libreoffice`. Keep a copy of an existing house BRD (e.g.
`WEB_PLACE_ORDER_INTRADAY_BRD.docx`) as the **style template**.

```bash
# 1. Author  brd.md  (grid tables per §9.1)

# 2. Convert with the house template + a TOC
pandoc brd.md -o brd.docx --reference-doc=HOUSE_TEMPLATE.docx --toc --toc-depth=2

# 3. Apply the house table look (navy header / zebra / bold / monospace code refs)
python3 apply_brd_look.py brd.docx

# 4. Verify faithfully (renders as Word would); eyeball a case page
soffice --headless --convert-to pdf --outdir . brd.docx
```

Verify in **LibreOffice or Word** — not an HTML preview. HTML converters add their
own borders and hide the missing style, which masks problems.

### 10.1 The post-processor — `apply_brd_look.py`

Pandoc emits unstyled tables; this stamps the house look onto every table by direct
cell formatting. Save it next to the BRD and run it as step 3.

```python
# apply_brd_look.py — stamp the Mynt house table look onto a pandoc docx:
# navy header (fill 1F3A93 + bold white), zebra body rows (F7F8FC alternating),
# bold first-column labels, monospace "Code Reference" values. Arg: the docx path.
import sys, re, zipfile

path = sys.argv[1]
NAVY, ZEBRA = '1F3A93', 'F7F8FC'

def shd(fill):
    return f'<w:shd w:val="clear" w:color="auto" w:fill="{fill}"/>'

def set_fill(cell, fill):
    if fill is None:
        return cell
    s = shd(fill)
    for empty in ('<w:tcPr/>', '<w:tcPr />'):
        if empty in cell:
            return cell.replace(empty, '<w:tcPr>' + s + '</w:tcPr>', 1)
    if '<w:tcPr>' in cell:
        return cell.replace('<w:tcPr>', '<w:tcPr>' + s, 1)
    return cell.replace('<w:tc>', '<w:tc><w:tcPr>' + s + '</w:tcPr>', 1)

def bold(cell, white):
    props = '<w:b/>' + ('<w:color w:val="FFFFFF"/>' if white else '')
    cell = re.sub(r'(<w:rPr>)', r'\1' + props, cell)
    cell = re.sub(r'<w:r>(?!<w:rPr>)', '<w:r><w:rPr>' + props + '</w:rPr>', cell)
    return cell

def mono(cell):
    f = '<w:rFonts w:ascii="Consolas" w:hAnsi="Consolas" w:cs="Consolas"/><w:sz w:val="17"/>'
    cell = re.sub(r'(<w:rPr>)', r'\1' + f, cell)
    cell = re.sub(r'<w:r>(?!<w:rPr>)', '<w:r><w:rPr>' + f + '</w:rPr>', cell)
    return cell

def celltext(cell):
    return ''.join(re.findall(r'<w:t[^>]*>([^<]*)</w:t>', cell)).strip()

def process_tbl(tbl):
    rows = re.findall(r'<w:tr\b.*?</w:tr>', tbl, re.S)
    out = tbl
    for ri, row in enumerate(rows):
        cells = re.findall(r'<w:tc>.*?</w:tc>', row, re.S)
        header = (ri == 0)
        zebra = (ri >= 1 and ri % 2 == 0)
        is_coderef = (len(cells) > 1 and celltext(cells[0]) == 'Code Reference')
        newrow = row
        for ci, cell in enumerate(cells):
            c = set_fill(cell, NAVY if header else (ZEBRA if zebra else None))
            if header:
                c = bold(c, True)
            elif ci == 0:
                c = bold(c, False)
            elif ci == 1 and is_coderef:
                c = mono(c)
            if c != cell:
                newrow = newrow.replace(cell, c, 1)
        if newrow != row:
            out = out.replace(row, newrow, 1)
    return out

z = zipfile.ZipFile(path); E = {n: z.read(n) for n in z.namelist()}; z.close()
doc = E['word/document.xml'].decode('utf-8')
for t in re.findall(r'<w:tbl>.*?</w:tbl>', doc, re.S):
    doc = doc.replace(t, process_tbl(t), 1)
E['word/document.xml'] = doc.encode('utf-8')
zo = zipfile.ZipFile(path, 'w', zipfile.ZIP_DEFLATED)
for n, d in E.items():
    zo.writestr(n, d)
zo.close()
print('styled', path)
```

## 11. Copy-paste skeleton

Author the body in Markdown like this. Case tables are grid tables (§9.1); a small
Python helper that wraps text and emits the `+`/`|` grid saves hand-alignment.

```markdown
# <Feature> — Business Requirements Document

## Document Control

| Field | Detail |
|---|---|
| Document Title | <Feature> — Business Requirements Document |
| Product | Mynt Plus — Web Trading Platform |
| Module | <module / sub-area> |
| Platform | Web |
| Owner | Zebu Trade |
| Last updated | YYYY-MM-DD |
| Status | Issued for Review |
| Classification | Internal Use Only |

## Scope

<what is covered — feature + surfaces + one-line context>

<coverage — default states, controls, scenarios, validations, common behaviours>

<organisation + out-of-scope + environment caveat>

# SECTION 1 — <NAME>

Note for the tester: <cross-cutting fact for every case in this section>.

## 1.1 <topic>

#### XX-001 — <concise behaviour> (<qualifier>)

+----------------------+-----------------------------------------------------------+
| Field                | Detail                                                    |
+======================+===========================================================+
| Description          | <2–5 sentences: what it does + context/rules.>            |
+----------------------+-----------------------------------------------------------+
| Test Steps           | 1. <concrete action>                                      |
|                      | 2. <concrete action>                                      |
|                      | 3. <observe …>                                            |
+----------------------+-----------------------------------------------------------+
| Expected Result      | - Step 1: <verifiable outcome>                            |
|                      | - Step 2: <verifiable outcome, "verbatim message" quoted> |
|                      | - Live — requires an open market.                         |
+----------------------+-----------------------------------------------------------+
| Code Reference       | file_one.dart:120-160, file_two.dart:45                   |
+----------------------+-----------------------------------------------------------+
```

## 12. Author checklist (before delivery)

- [ ] Document Control has all 8 fields; date/status/classification current.
- [ ] Scope states in-scope and out-of-scope clearly; **no legacy-version narration**.
- [ ] Each section has a `Note for the tester:` where a cross-cutting fact exists.
- [ ] Case IDs use one prefix, are zero-padded, gapped between groups, and unique.
- [ ] Every case has all four rows: Description, numbered Test Steps, per-step
      Expected Result, Code Reference.
- [ ] UI/validation messages quoted verbatim; mirror cases reference their primary.
- [ ] Environment/market-hours cases marked.
- [ ] **No** RTM / BR / NFR / priority-tag scaffolding unless explicitly requested.
- [ ] **No** embedded credentials or live URLs.
- [ ] Converted with `--reference-doc` + `--toc`, post-processed with
      `apply_brd_look.py`, and **verified in LibreOffice/Word** — tables show the
      navy header, zebra rows, bold labels, and monospace code refs.
